- **`/panel-manager` est dans `maintenanceExcludes`** (`middleware.ts`) : le CMS
  reste accessible **pendant la maintenance**. Ne jamais désactiver la
  maintenance pour verser des photos.
- **Déjà utilisé** : 1 394 photos Monténégro importées le 2026-09-30, + Roumanie
  (147) et Lisbonne (50). `cms_media.source = 'gphotos'` pour 1 595/1 601.

### Le piège du champ `destination`

Ce n'est **pas** une page, c'est un **dossier** :
`dossier = destination.replace(/[^a-z0-9-]/gi,'').toLowerCase()` →
`destinations/<dossier>/`. Champ libre → un `Madère` mal saisi crée un dossier
en double. Pour les sous-pages : taper le **parent** (`madere`, `idf`,
`normandie`, `porto`), jamais `madere-funchal`.

### Rien n'est automatique après l'import

- **Couverture** : `heroImage="/og-default.jpg"` est **en dur** dans les 23
  `page.tsx`. Aucun code ne rattache une photo importée à une page. À poser à la
  main (zone `hero_image`).
- **Pépites** : les 3 titres génériques existent **en dur dans `page.tsx` ET en
  zones CMS**. Le CMS **prime** (`zones[key] ?? fallback`) → corriger en base,
  pas dans le code.

## Le piege du build vs production (majeur)

Le HTML prerendu par `npm run build` ne reflete PAS la production. Le build local
n'a pas de `SUPABASE_SERVICE_ROLE_KEY` (`.env.local` = 3 variables publiques) :
`getPageZones()` utilise le client **service** -> stub -> aucune zone lue -> les
pages montrent les **fallbacks codes en dur**.

En production, la zone CMS **ecrase** le fallback (`value = zones[key] ?? fallback`).
Donc quand code et base divergent, le build montre le code, la prod montre la base.

Regle : pour juger un rendu, lire la valeur EN BASE (REST + cle publique suffit)
ou lancer `next start` avec la cle service. Ne jamais conclure d'un `.next/*.html`.

Cas concret : 5 pages Madere/Roumanie affichent `/og-default.jpg` (zone ecrite le
2026-08-19) alors que leur page.tsx porte deja une vraie photo HTTP 200.

## Les cles legacy sont DESACTIVEES cote Supabase (2026-10-17)

**C'est la cle de l'incident d'aout.** Elle porte `service_role` mais Supabase

meme ou l'incident documente dans `AGENTS.md` a ete traite. Une cle legacy
`service_role`, meme valide en signature, **ne peut plus rien ecrire**.

### Consequence pratique

- Pour ecrire, il faut une cle **nouveau format** : `sb_secret_...`
  (Dashboard -> Settings -> API Keys). Pas de JWT legacy.
- Ne PAS « Re-enable legacy API keys » pour depanner : ce serait rouvrir
  exactement le trou ferme le 19/08.
- Le CI fonctionne parce que le secret GitHub nomme `SUPABASE_SERVICE_ROLE_KEY`
  contient vraisemblablement une `sb_secret_...` (nom historique, valeur neuve).
  C'est le pattern adaptatif de `lib/supabase-key.ts`.

### Comment reconnaitre une cle qui peut ecrire

| Ce qu'on a | Ce que ca vaut |
|---|---|
| `sb_publishable_...` (46 car.) | lecture seule, RLS |
| JWT `eyJ...` role service_role | **mort** depuis le 19/08 |
| `sb_secret_...` | ecriture, contourne la RLS |
| `sbp_...` | compte, pour la CLI / Management API |

Test decisif pour toute cle : `INSERT` d'une ligne jetable -> 401 `42501`
= pas d'ecriture ; 201 = ecriture reelle. Ne jamais se fier au prefixe ni au
nom de la variable.

## 5e PIEGE DU PARSEUR SQL (le plus dangereux)

En plus des 4 pieges deja notes (split sur `;`, split sur `,`, apostrophe
echappee dans LIKE, `on_conflict` obligatoire) :

**Le parseur de `VALUES` s'arretait au premier `)`.** Or une valeur peut en
contenir : « Les Églises en bois UNESCO (Bârsana & Ieud) ». Consequence : le
tuple etait rejete (nombre de valeurs incorrect) et la zone **silencieusement
OMISE** — 25 tuples lus au lieu de 24, et un tuple perdu.

Corrige : `decouperTuples()` suit les litteraux ET la profondeur des parentheses.
Garde-fou ajoute : le script **refuse de continuer** (`exit 4`) si le nombre de
tuples lus differe du nombre de zones attendues, au lieu de continuer en
silence.

Verifie a posteriori que `140000` (DEJA appliquee avec l'ancien parseur) n'avait
pas ete touchee : comparaison base vs migration -> 56/56 lignes, 0 manquante,
0 valeur differente. Saute par chance : aucune de ses valeurs ne contient `)`.

## `ON CONFLICT` DANS LES COMMENTAIRES

`stmt.indexOf('ON CONFLICT')` matchait le **commentaire d'en-tete** (« Idempotente :
ON CONFLICT (page, zone_key) DO UPDATE ») et non la clause reelle, ce qui
tronquait le corps a zero. Toujours chercher l'occurrence APRES `VALUES`.
