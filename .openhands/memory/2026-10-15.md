## Découvertes marquantes

### Cause racine n° 1 — heros vides invisibles
7 pages pointaient vers `/images/...` alors que le fichier n'existe que dans
Storage. Aucun rewrite `/images/→Storage` dans `vercel.json`. Et `ZoneImage`
masque l'image en `onError` : donc **trou vide, pas d'icône cassée**. Un contrôle
visuel ne l'aurait jamais vu. Corrigé (URLs Storage, 200 vérifiés).

Méthode qui a marché : pour chaque chemin local cassé, tester si le **même nom de
fichier** existe dans `media/` ou `blog-images/` du bucket. 7 sur 39 étaient dans
ce cas, et pour chacun la ligne CMS de la même destination référençait déjà l'URL
Storage — corroboration indépendante, donc remplacement non inventé.

### Cause racine n° 2 — contenu engendré depuis un gabarit
- 37 sous-pages partagent la même fin de `<meta description>`.
- 9 publient une étiquette **interne** dans la description (« ⭐ Secret Gem »,
  « ⭐ Hidden Gem »). Le badge public est « ⭐ Coup de cœur » (`status='starred'`).
- 37 des 43 sous-pages partagent le même `localTip` ; 44 descriptions de highlight
  font < 28 caractères (« Or. », « Vue. », « Dune. »).
- 11 articles ont une consigne de rédaction restée en `<h2>` visible.

Rien de tout cela n'est corrigeable par un script : c'est un travail de rédaction.

### Cause racine n° 3 — filtre sur un champ inexistant
`app/sitemap.ts` filtrait sur `post.status` qui n'existe pas sur `BlogPost` ;
repli sur `published_at`, donc 2 articles publiés sans date disparaissaient du
sitemap. Corrigé via `selectSitemapPosts()` + test de non-régression.

### Méthode qui a payé : croiser les redirections avec le sitemap
`next.config.js` a 32 redirections permanentes. En croisant **les 32** avec **les
119 URLs du sitemap de production**, on trouve 2 articles indexés alors qu'ils
sont redirigés en 301. La version antérieure de l'audit n'en avait vu qu'un
(seul un `grep stoos` avait été fait). Garder ce croisement systématique.

## Erreurs de méthode commises puis corrigées

1. **Scan de liens cassés trop permissif.** Mon premier script traitait
   `/destinations/[slug]` comme consommant n'importe quel chemin sous
   `/destinations/`, donc il ne trouvait rien. Un segment dynamique ne consomme
   que **ses propres** segments. Le scan strict (nombre de segments égal) a
   trouvé les liens `viscri`/`sighisoara`. Toujours valider un « zéro problème »
   en vérifiant que le détecteur sait détecter.
2. **Sévérité surévaluée.** J'ai classé `viscri`/`sighisoara` en P1 avant de
   vérifier **qui consomme** le champ `link`. Réponse : personne côté public,
   seulement le formulaire admin. Le lien n'est jamais rendu → P3. Vérifier le
   consommateur avant d'estimer l'impact.
3. **Une seule redirection croisée, pas toutes.** J'avais annoncé 1 article
   indexé-puis-redirigé ; en croisant **les 32** redirections avec **les 119**
   URLs du sitemap, il y en a 2.

## P0 découvert en fin de session — le site était DOWN, pas « en maintenance »

Vers 21:15 UTC, `heldonica.fr` renvoyait **504 MIDDLEWARE_INVOCATION_TIMEOUT**
(25,1 s) sur toutes les routes de contenu — pas un 307 vers /maintenance.

Chaîne de preuves :
1. `x-vercel-error: MIDDLEWARE_INVOCATION_TIMEOUT` dans les en-têtes → le
   middleware, pas la page.
2. Corrélation parfaite : tout endpoint qui interroge Supabase pend
   (`/api/destinations`, `/api/cms/pricing` > 75 s) ; tout endpoint qui répond
   sans la base répond vite (`/api/og` 200 en 3,2 s, sans appel Supabase).
3. Interrogation directe de la base avec la clé **valide** :
   `storage/v1/bucket` → **544 DatabaseTimeout** ; `rest/v1/site_settings` →
   aucune réponse > 90 s. Avec une clé **bidon** : 401 en 0,07 s. La passerelle
   est saine, la **base** non.
4. Cause racine : `getMaintenanceMode()` (`lib/supabase-edge.ts`) interrogeait la
   base **sans délai d'expiration**, à **chaque requête** → Vercel tue la
   fonction Edge avant que le repli (page de maintenance) ne s'exécute.

Fenêtre : la base répondait encore à 16:43 UTC (captures `.audit/` réussies,
41 articles + 41 destinations + 1000 zones) ; injoignable à 21:15. Panne survenue
entre ces deux moments.

Corrigé dans la branche (plafond 3 s), **non déployé**. Vérifié en local en
simulant une base injoignable : 307 → /maintenance en 3,0 s. Test
`__tests__/lib/supabase-edge-maintenance.test.ts`. La remise en route de la base
revient au propriétaire (tableau de bord Supabase).

Leçon : la clé publique Supabase (`sb_publishable_…`) est **livrée dans le bundle
client** — donc lisible. Utile pour sonder la base sans identifiants privilégiés,
mais rappel que ce n'est pas un secret. La clé *service_role* ne l'est pas.
